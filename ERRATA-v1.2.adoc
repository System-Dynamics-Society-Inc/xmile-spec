= Errata: XMILE Version 1.2
:toc:
:sectnums:

Four common style attributes had two spellings each. Chapter 5 and the schema
recognized one, and every element example in Chapter 6 wrote the other, so a
file that copied an example from the specification was rejected by the schema
published with it.

This has been corrected in Release Candidate 01. Chapter 6 now uses the names
Chapter 5 defines: `+padding+`, `+border_color+`, `+border_width+` and
`+border_style+`. This file records what was inconsistent, what was done, and
how the `+text_+` spellings should now be read.

[IMPORTANT]
====
This is a different kind of defect from the one recorded in `ERRATA-v1.1.adoc`.
That was a broken reference: text pointing at a section that had been deleted,
which a build can detect. This one was a duplicate name, where both spellings
were documented and neither was wrong on its face. No build catches it, and no
reader notices until two implementations exchange a file.
====

== What was inconsistent

Chapter 5, in Common styles associated with all XMILE display objects, defines
the style attributes every display object may carry. Chapter 6 opens with a list
of the same attributes, most of which say only "defined in Chapter 5". Four of
them said something else:

[source,asciidoc]
----
* text_padding      - same as padding      as defined in Chapter 5
* text_border_color - same as border_color as defined in Chapter 5
* text_border_width - same as border_width as defined in Chapter 5
* text_border_style - same as border_style as defined in Chapter 5
----

The second name was deliberate, not a typographical slip. The likely reason is
visible in the same list: `+text_align+`, `+text_background+`,
`+text_decoration+` and `+vertical_text_align+` genuinely do carry the `+text_+`
prefix in Chapter 5, so four neighboring attributes were given a matching
prefix. The difference is that those four are the names Chapter 5 defines, and
these four were not.

All nine element examples in Chapter 6 then wrote the long names, and none
validated against the schema:

[cols="1,1",options="header"]
|===
| Example | Section
| `+<stock>+` | Stock
| `+<flow>+` | Flow
| `+<aux>+` | Aux
| `+<module>+` | Module
| `+<group>+` | Group
| `+<connector>+` | Connector
| `+<slider>+` | Sliders
| `+<numeric_display>+` | Numeric Displays
| `+<text_box>+` | Text Boxes
|===

== What was done

. *The short names were chosen.* Chapter 5 defines them, the schema implements
them, and they match `+border_color+` and its siblings on every other object.

. *Chapter 6's attribute list was corrected.* The four "same as" lines now name
`+padding+`, `+border_color+`, `+border_width+` and `+border_style+`, each
"defined in" Chapter 5 like every other entry in the list.

. *The examples were corrected.* All 36 uses of the long names in the nine
examples above, four attributes in each, now use the short names.

. *Chapter 5 and the schema were not changed.* They already used the short
names.

== How the `+text_+` spellings read now

The open question this errata originally asked, whether the `+text_+` prefix was
meant to mean something, has been answered by the Style Prefix Additions section
of Chapter 5, added in this release. It makes `+text_+` one of a list of
prefixes that apply a style attribute to one part of an object.

So `+text_padding+` is no longer a second spelling of `+padding+`. It is the
padding of the object's text elements only, and it overrides `+padding+` for
them. The same holds for `+text_border_color+`, `+text_border_width+` and
`+text_border_style+`. The schema declares these as prefixed attributes.

A file written to an earlier draft that used the long names on an object
therefore still validates. A reader that applies the prefixes as described in
Chapter 5 will apply those values to the object's text rather than to the whole
object. For most objects, whose text is a single label, the visible result is
the same.

== The table header attributes

Chapter 6 describes the style of a table header in one sentence, as the
attributes of Chapter 5 prefixed with `+header_+`. While four of those
attributes had two names, that sentence had two readings, and files in
circulation resolved it the other way from the schema.

The Style Prefix Additions section resolves this too. It names `+header_+`,
`+header_font_+` and `+header_text_+` as separate prefixes, so
`+header_padding+` and `+header_text_padding+` are both valid and mean different
things: the header as a whole, and the text within it.

== Still worth doing

* *Add a check.* This defect was mechanically detectable: every attribute name
written in a specification example should be declared in the schema, and every
attribute the schema declares should appear somewhere in the specification. A
lint over the two would have caught this on the day the alias was introduced, as
it would have caught `+max_dimensions+` against `+maximum_dimensions+`. The
Chapter 6 examples use typographic quotation marks, so such a check would first
need to normalize them, or the examples would need correcting as well.
